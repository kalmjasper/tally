New in v7: auto-label rules

A rules table ("counterparty contains pattern → category", or "→ transfer to a pot") and a rule_id on transaction_splits and link_groups that records which rule set a label or made a transfer. Rules only fill transactions without a category that aren't in a link group; they run on import and when a rule is created; the longest pattern wins. Full design: auto-label proposal.

New in v6: savings pots

Money you keep outside the accounts you import, such as savings or cash, lives in a pot: an ordinary account you never import. One nullable column links a one-sided transfer to it.

What changed in v5: simplicity review

An adversarial review looked for anything we don't need yet. Everything removed here can come back through a migration or a compatible proto field; see Deferred.

ParsersEach accepts exactly the real export format: ING in English, comma-separated, YYYYMMDD; AMEX Datum,Omschrijving,Bedrag with month-first dates. No header aliases, delimiter guessing or encoding fallback. Both real files import completely.
No adapter traitTwo plain parse(&[u8]) functions; core picks one by source id. Each parser writes its own full key, ing_csv:v1:….
Removedaccounts.kind, transactions.updated_at, manual transactions (so import_batch_id is required), the Tikkie suggester (reimbursements are linked by hand), pagination, the key-version guard, orphan-group cleanup on undo, down migrations, CORS, the ListSources RPC.
KeptSplits and default reimbursement splits, the transfer suggester (on real data: every credit-card bill payment, plus the odd false positive), group rules, the report query, idempotent imports.

Design principles

Only what the first version needs: import ING and AMEX without duplicates, categorize, and link transfers and Tikkies. Everything else is listed under Deferred, with the moment we'd add it through a migration.

One row per real movementA transaction is exactly one line from a bank or card statement. Its amount is signed from that account's point of view.
Groups give meaningA transaction can point to one link_group (transfer or reimbursement). The sign of the amount gives the role, so no join table is needed.
Idempotent with one keyUnique (account_id, import_key) on transactions, plus a file hash on import_batches. Each parser builds its own versioned key. Each import runs in one DB transaction: all or nothing.
Categories live on splitsA transaction gets its category through one or more transaction_splits that add up to its amount. A transaction with no splits is uncategorized.
Keep the raw rowEach transaction stores its original source row as jsonb. Nothing we don't parse yet (FX, balance-after) is lost, and we can backfill new columns later.

Import flow and parser interface

Each source is one function from file bytes to normalized rows. Everything after parsing is shared. A trait comes back when the aggregator API arrives.

pub struct NormalizedMutation {             // the account comes from the upload, not the row
    pub key: String,                         // "{parser}:v{n}:{key}", stable across overlapping exports
    pub booked_on: jiff::civil::Date,
    pub amount_cents: i64,                   // signed cents from this account's view
    pub counterparty_name: Option<String>,
    pub counterparty_iban: Option<String>,
    pub description: String,
    pub raw: serde_json::Value,              // the original row
}

Reporting rules

Reports are computed, not stored. With splits, category totals are plain sums. The groups only decide what's excluded and which month an amount lands in.

Category totalΣ transaction_splits.amount_cents per category and month. A positive split (a Tikkie, a refund) reduces the spending in its category. If you get back more than you paid, the category can end up positive for that month.
Transfer groupExcluded from all income and expense reports. Members have no splits.
MonthThe transaction's booked_on. Exception: members of a reimbursement group count in the month of the group's earliest negative member. A group with only positive members uses each member's own date.
Default Tikkie splitsA positive member without splits gets them filled pro rata over the negative members' splits when it joins a group. Cents are rounded with the largest-remainder method, so the splits always add up exactly.
UncategorizedTransactions without splits that aren't in a transfer group. Shown as two buckets, "Uncategorized in" and "Uncategorized out", so incoming and outgoing money don't cancel out.
BalanceNot in v1. The balance-after column is kept in raw, so it can be added later.

Backend structure (implemented)

A Cargo workspace with five crates. Dependencies only point down: sources knows nothing about the database, only core queries it, and the gRPC handlers in server stay thin.

Solid arrow = depends on / calls. Dashed = generated by a script, not a Cargo dependency.

Crates

Conventions

Proto versioningpackage finance; without a v1 suffix. Frontend and backend ship together, so compatible changes (new fields, never reusing field numbers) are enough.
Moneyint64 amount_cents in proto, i64 in Rust, bigint in Postgres. EUR only in v1.
Dates and timesA Date {year, month, day} message for booking dates, google.protobuf.Timestamp for timestamps. jiff in sources, core and server.
Errorscore::Error = NotFound | InvalidArgument | FailedPrecondition | Database, mapped 1:1 to tonic status codes. A group-rule violation is FailedPrecondition with a readable message.
Testssources: unit tests on the statement fixtures, including "two overlapping exports give the same keys". core: integration tests on real Postgres via test-all; each test creates and migrates its own database, so tests run in parallel, and all data enters through import_file. Proto: buf lint. Migrations only run forward.
Dev loopdirenv allow → devenv up (local Postgres) → cargo run -p tally-server (cargo goes through the mbx build cache). After editing a migration: generate-entities.

Open questions

  • jiff and SeaORM (decided: option 1). SeaORM 2.0.4 only supports chrono and time column types, so the generated entities use chrono and tally-core's time module converts at the boundary. Everything above entity sees jiff only.
  • Pending AMEX charges. The current export shows no pending rows. If a later export includes a pending charge that changes once it posts (amount, date or description), it would be imported twice. Check when you next see one.
  • A transaction can be in at most one group. Using an FK enforces this structurally. If one bank transfer from a friend covers two dinners, put both dinners in one group.
  • IDs are bigint identity columns, exposed as int64 in proto.
